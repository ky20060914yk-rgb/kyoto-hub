# 京大InfoHub 再設計 — 設計ドキュメント

- 日付: 2026-09-07
- 対象: kyodai-info.web.app（Flutter Web + Firebase、`kyoto_exam_hub`）
- ステータス: ブレインストーミング完了、レビュー待ち
- 前提: 実績ほぼゼロ（友人数名のみ）、ソロ開発、無資金、収益は将来的に企業広告

---

## 1. 背景と現状

### 現状のプロダクト
京大生（`@st.kyoto-u.ac.jp` 限定）向けの過去問・資料共有アプリ。以下を実装済み:

- KULASIS 由来の時間割（約1万科目、`kulasis_dataset.dart` に 10,170 行ハードコード）
- 科目ごとの過去問 / テスト対策情報 / その他情報の投稿・ダウンロード
- 参考書の貸し借り（リクエスト → 応答時に一律 20pt 決済 → トークルーム）
- 資料リクエスト掲示板（報酬ポイント設定つき）
- ポイント経済（登録 +30、投稿 +5、DL −5、アップローダーに 80% 還元、5DL/10DL マイルストーン、招待 +10、通報 3 件で自動削除＋ポイント没収）
- メール認証、通報 / お問い合わせ

### 創業者が実感しているペイン
1. **過去問がなくても「情報」だけ欲しい**（教授の癖、持ち込み可否、出席の重さ、過去問流用度など）
2. **教科書の売買・貸し借りを、知り合いがいなくても安全にやりたい**

### このドキュメントの目的
現状の「過去問 PDF 共有ツール」を、**京大生の履修・試験まわりの意思決定を助けるアプリ**へ再設計する。

---

## 2. ゴールと非ゴール

### ゴール
- テキストの授業情報（レビュー）を**摩擦ゼロで書け・読める**基盤を作る
- 過去問・資料層を**サーバー権威の軽量クレジット**に作り直し、セキュリティの穴を塞ぐ
- 教科書の売買を**独立した差別化機能**として提供する
- 科目の同一性（Course エンティティ）を正しくモデル化し、貢献が分散しないようにする
- 2026 年 10 月（後期履修登録期）に**レビュー層で本番ローンチ**する

### 非ゴール（今回やらない）
- 多大学展開（`universityId` フィールドは残すが、設計は京大のみを前提にする = B1）
- 収益化機能の実装（企業広告は将来。今回はアーキテクチャに影響しない範囲でのみ考慮）
- ネイティブアプリ（iOS/Android）の本格対応
- Flutter Web からの技術スタック移行（Phase 1 後に再評価）
- AI 機能

## 3. 意思決定ログ

| 論点 | 決定 | 理由 |
|---|---|---|
| 過去問の著作権スタンス | **A3: 折衷**。PDF は許容するが、教員・大学からの削除要請は即応。収益化（広告）は過去問と切り離し、サイト全体に対して行う。クレジットは金銭で購入不可 | リスクを取りつつ、営利で過去問アクセスを販売する形は避ける |
| 目指す規模 | **B1: まず京大で完全に回す**。横展開は成功後、設計に含めない | ソロ・無資金。Penmark 等との多大学での殴り合いは非現実的 |
| 課金モデル | **2 層モデル**。テキスト情報 = 投稿も閲覧も無料 / PDF 層 = 軽量クレジット（give-to-get、サーバー集計） | 軽い貢献は無報酬 UGC で回る（食べログ等）。読むのに課金するとレビューが死ぬ。ポイント経済は流動性がある前提の調整機構であって、市場を作れない |
| 教科書機能 | **独立タブ**。売買・譲渡が中心、貸し借りは v1 見送り。決済はアプリ外 | 差別化の目玉。集客フックなのでノータックス（現状の 20pt 決済は廃止） |
| ローンチ戦略 | **段階ローンチ**。10 月 = レビュー層のみ / 1 月 = 過去問クレジット / 4 月 = 教科書マーケット＋フル集客 | 全部を 1 ヶ月ソロでは不可能。一度きりの初速を無駄にしない |
| 技術スタック | **Flutter Web + Firebase を維持**。Phase 2 で Cloud Functions（TypeScript）を追加 | 既に動作。この規模では十分。書き直しは 10 月に間に合わない |

## 4. 全体設計

### 4.1 情報アーキテクチャ / ナビゲーション

**下タブ（4 枠）** — `お問い合わせ` はタブから外しマイページへ:

| タブ | 中身 | 役割 |
|---|---|---|
| さがす | 全科目の検索＋ランキング（楽単・過去問が多い・レビューが多い・新着）。ログイン直後でも閲覧可 | 集客の玄関。履修を決めていない新入生が最初に触る |
| 時間割 | 自分の週グリッド。各コマに「新着レビュー / 過去問」バッジ。空きマスをタップ → 検索 → 登録、既存マスをタップ → 科目詳細 | 保持装置。毎日開く理由 |
| 教科書 | 出品一覧（譲る / 売る / 買いたい）。独立機能（Phase 3） | 差別化の目玉 |
| マイページ | プロフィール、クレジット残高、自分の貢献、設定、お問い合わせ | — |

- アプリバーに**ベルアイコン**（通知: 「リクエストした過去問が来た」等）。再訪トリガー
- **時間割のマスをタップして登録するフロー**は維持する。登録対象が正規化された Course になる点だけ変わる

**科目詳細画面** — 現状 3 タブ（過去問 / テスト対策 / その他）を **2 タブに再編**:
- **レビュー**（構造化フィールド＋自由記述、無料、デフォルト表示）
- **過去問・資料**（PDF、クレジット消費）
- 曖昧な「テスト対策 / その他」の区別は廃止

**2 層の UI 上の現れ**（クレジット周りは Phase 2 で有効化。Phase 1 では過去問は現行のポイント制のまま）:
- 認証済み京大生は**レビューも教科書も 0 クレジットで全て読める**
- レビュー投稿 = 無料。過去問 DL = 1 クレジット消費、アップロードで補充
- 新規は**お試しクレジット 3**（初日にカタログが有料の壁に見えないように）

### 4.2 授業情報層（テキスト）— Phase 1

**レビューの構造化フィールド**（1 科目 1 レビュー、後から編集可）:

| 項目 | 選択肢 |
|---|---|
| おすすめ度 | ★1〜5 |
| 楽単度 | 楽 / 普通 / 難 |
| 出席 | 取らない / 取る（ゆるい）/ 毎回（重い） |
| 成績のつけ方 | 試験一発 / 試験+レポート / レポート中心 / 出席点大きい |
| 過去問の効き | ほぼそのまま / 類題が出る / 傾向把握に有用 / 効かない・不明 |
| 持ち込み | 不可 / 可 / 該当なし |
| コメント | 自由記述（任意、推奨） |
| 履修時期・評価 | 例: 2024 前期・A（任意。信頼度表示に使う） |

- 科目詳細では各項目を**集計表示**（分布バー＋平均）。「楽単スコア」を自動算出
- 各レビューに**「役に立った」ボタン** → 投稿者の貢献スコアに加算（バッジ・ランキング）

**「さがす」タブ:**
- ランキング: 楽単（学部別 / 全学共通の系列別）、過去問が多い科目、レビューが多い科目、新着レビュー
- 検索: 科目名・教員名
- フィルタ: 学部 / 曜限 / 全学共通の系列（人文・社会・自然・言語…）

**秩序・不正対策:**
- 認証済み京大生のみ投稿、1 人 1 科目 1 件、レート制限
- 通報 → 閾値で非表示＋運営キュー
- レビューは「意見」なので PDF より法的リスクは低い。モデレーションは軽め

### 4.3 過去問・資料層 ＋ クレジット — Phase 2

**保存するもの:** Course に紐づく PDF/画像。カテゴリ = 過去問（年度・学期・種別: 中間/期末/追試）or 資料（解答・まとめ・レジュメ）。年度＋種別で重複排除。

**クレジット（サーバー権威に作り直す）:**

| 動作 | 増減 |
|---|---|
| 新規登録 | +3（お試し） |
| 資料を DL | −1（種類問わず一律） |
| 資料をアップ（承認時） | +3（1 日の付与上限あり、重複投稿は対象外） |
| レビュー投稿（最初の 3 件） | 各 +2（1 ユーザー 3 件まで。2026-10-03 変更: 当初は「初回 1 回だけ」） |
| レビュー投稿（総レビュー数 5 件以下の科目） | +1（データ収集のため。科目画面に「レビュー募集中」タグ。レビューボーナスは 1 日 5 回まで） |
| 自分の投稿・自分がリクエストした資料 | 無料 DL |

- **廃止**: 80% ロイヤリティ / 5DL・10DL マイルストーン / 削除ペナルティ / 2020 年カットオフ / 投稿者が 0〜20pt を設定する仕組み。一律 1 クレジット、付与は固定
- **クレジットは金銭で購入できない**（A3 の線引き）

**ストレージのセキュリティ（現状の穴を塞ぐ）:**
- ファイルは**非公開バケット**に置く
- DL は Cloud Function 経由: `ku_verified` クレーム確認 → トランザクションで残高 −1 → 台帳記録 → **10 分の署名 URL** を返す
- 「URL を知っていれば誰でも DL」を廃止

**リクエスト掲示板（簡素化）:**
「2023 年度の◯◯が欲しい」を投稿（無料）。誰かが応じる → 提供者に +3 クレジット、依頼者は無料 DL。**報酬 pt を賭けるスライダーは廃止**（固定）。

**削除対応フロー（A3）:**
- 全資料に「報告」ボタン＋「担当教員・権利者の方はこちら」フォーム
- 権利者・大学からの要請 = **優先キュー、即時削除**。投稿者に通知。**獲得済みクレジットは没収しない**
- 一般通報は閾値で非表示＋運営確認

### 4.4 教科書マーケット（独立タブ）— Phase 3

- **出品タイプ:** 譲る（無料）/ 売る / 買いたい（リクエスト）。「貸す」は返却管理・保証金・トラブル対応が重いので v1 見送り
- **出品フィールド:** 本のタイトル（自由入力）/ 関連科目（任意、Course 参照）/ 状態（新品同様〜書き込み多め）/ 価格（売る場合、定価が上限の推奨）/ 写真 / 受け渡し場所（時計台前・生協前・各学部棟…プリセット）
- **一覧・マッチング:** 科目フィルタ、フリーワード。「買いたい」に合致する出品が出たら通知。話がついたらチャット
- **金銭・安全:**
  - 決済はアプリ外（現金手渡し / 個人間送金）。アプリは金銭を扱わない・エスクロー無し。UI に明示
  - 現状の「応答時に一律 20pt 決済」は**廃止**。教科書は完全無料・ノータックス
  - 認証済み京大生のみ / 取引後に相互評価（★＋一言）/ 通報 / 「受け渡し不履行」報告 → 運営対応
  - 出品は 30 日で「まだ有効?」通知、期限切れ非表示 / 教科書以外の出品禁止

### 4.5 データモデル / アーキテクチャの作り直し

#### 4.5.1 Course エンティティ（最重要）
`ku_official_N` の連番を廃止。**`courseKey = normalize(科目名) + 主担当教員`** を安定キーにする。

```
Course {
  id, courseKey,
  name, lecturers[], faculty, series,          // series = 全学共通の系列
  syllabus: { credits, term, evaluationMethod, summary },  // 後フェーズで各シラバスURLをスクレイプして流し込む
  slots: [{ day, period, term }],              // 時間割表示用の非正規化
  stats: { reviewCount, avgRating, rakutanDist, resourceCount, ... }  // 集計キャッシュ
}
```

**データ現実（2026-09-07 調査）:**
- ソースの `syllabus_data.json`（11,663 件）は**ほぼ全学共通科目のみ**（専門科目 58 件）。既存の変換スクリプトは教員名を欠損時に捏造し、学部を科目名の正規表現で推定していた
- **Phase 1 の Course は `name / lecturers[] / faculty(実データ) / slots[]` のみ**。学部・教員の捏造はしない（欠損は「担当教員不明」）
- `series`、`syllabus.*` は後フェーズ（各 URL の個別スクレイプが必要）
- Phase 1 のカバー範囲は当面**全学共通科目**（新入生のレビュー対象と一致）

- レビュー・資料・教科書出品は**すべて courseId に紐づく**（曜日×時限のコマではなく）
- 年度をまたいでレビューが集計される（2022 と 2024 の「微積 A・教員 X」は同じ Course）
- 時間割のマス = `{ slotKey → courseId }` の参照だけ

#### 4.5.2 科目マスタの持ち方
- `kulasis_dataset.dart`（1 万件ハードコード = JS バンドル肥大の主因）を廃止 → **Firestore の `courses` コレクション**に一度だけ seed（管理スクリプト。毎起動 seed は削除）
- クライアントは検索時にクエリ取得＋キャッシュ。初回ロードが軽くなる
- 既存の `.py` スクレイパ＋`syllabus_data.json` から**クリーンなビルドスクリプト**を 1 本用意

#### 4.5.3 セキュリティルール（現状: 無し → 必須）
- **Phase 1**: カスタムクレームは Cloud Function が必要なため使わない。ルールは `request.auth.token.email` が `@st.kyoto-u.ac.jp` で終わること＋`request.auth.token.email_verified == true` を直接見る
- **Phase 2 以降**: メール検証時に Cloud Function が**カスタムクレーム `ku_verified`** を付与し、ルールをそれに移行
- `courses`: 認証済み読取のみ / 書込は管理者
- `reviews`: 読取 = 認証済み全員、作成 = `ku_verified` かつ 1 人 1 科目 1 件、更新・削除 = 本人
- `resources`: メタは読取可、**ファイル本体は Function 経由のみ**
- `credits_ledger` / `users.credits`: **Function のみ書込**
- `textbook_listings` / `chats`: 当事者のみ書込
- 全て `request.auth` 必須。可能なら `ku_verified` クレームで一段絞る

#### 4.5.4 クレジットは Cloud Functions で
- `downloadResource(resourceId)`: クレーム確認 → トランザクションで残高 −1 → 台帳記録 → 10 分署名 URL を返す
- アップ承認時: 日次上限つきで加算 → 台帳記録
- クライアントは残高を**一切書かない**（現状のクライアント権威 = 不正し放題を解消）

#### 4.5.5 その他
- チャットは `chats/{id}/messages/{msgId}` **サブコレクション**＋ページネーション（配列 `arrayUnion` を廃止。1MB 上限と競合を回避）
- 全件購読（`streamPosts`、`streamSubjects` 等）を廃止 → courseId でクエリ＋ limit。ランキングは**集計ドキュメントを事前計算**（onWrite Function またはスケジュール実行）
- `AppStore`（1000 行超の god object）を機能ごとの repository に分割（優先度: 中。まず 4.5.1〜4.5.4）

**着手順:** セキュリティルール ＋ Course 正規化 → クレジット Function → 署名 URL → チャット → AppStore 分割

## 5. 現状コードの問題点（棚卸し）

Phase をまたいで解消していく既知の問題。

### アーキテクチャ
- `AppStore` が全コレクションをメモリ保持し、`streamPosts()` 等がページネーション・limit 無しで全件購読。数百件で重く、数千件で破綻
- `seedKulasisSubjectsMaster()` が毎起動で約 1 万件を batch 書き込みしようとする（batch 上限 500 のため実際は例外、`.catchError((_){})` で握り潰し）
- Firestore セキュリティルールがリポジトリに存在しない（コンソール管理。テストモードのままなら DB 全体が素通し）→ **Phase 1 で最優先対応**
- ポイント経済が完全にクライアント権威。`users/{uid}.points` を直接書き換え、さらに他人のプロフィール（アップローダー報酬）も書き換える
- Storage のファイルが実質公開。DL 時に公開 URL を組み立てて開くだけで、ポイントゲートはクライアント側の見せかけ
- `talk_rooms.messages` を 1 ドキュメント内の配列で `arrayUnion` 追加（1MB 上限・競合）
- Email-link サインインと password + 検証メールの 2 経路が中途半端に混在

### プロダクト / UX
- **投稿がファイル添付必須**（`course_detail_screen.dart`: `selectedFiles.isEmpty ? null : ...`）。テキストだけの TIPS を投稿できない = ペイン #1 に構造的に反する → **Phase 1 のレビュー機能で解消**
- 構造化された授業レビューが無い。教授エンティティ無し、評価無し
- 科目の同一性が弱い（`ku_official_N` 連番、同名科目多数、年度情報無し）→ 貢献が「コマ」に分散
- 教科書はリクエスト型のみ。出品一覧が無い。完了確認・評価・紛争処理が無い。主需要である売買に対応していない
- 下タブの一等地が「お問い合わせ」。フィード / 通知タブが無い
- 通知が無い → 再訪の理由が無い
- ログインゲート＋重い Flutter web → SEO・シェア流入ゼロ
- スクレイプ済みの `syllabus_data.json`（単位数・開講期・成績評価方法・シラバス本文）をアプリが未使用

## 6. フェーズ別ロードマップ

### Phase 1 — 2026 年 10 月（後期履修登録期）: レビュー層で本番ローンチ

**スコープ (must):**
1. Firestore セキュリティルールの整備（最優先。DB 素通しの解消）
2. Course 正規化の最小版（レビューが年度をまたいで集計される程度）
   - `.py` スクレイパ＋`syllabus_data.json` から `courses` コレクションを生成する build スクリプト
   - `kulasis_dataset.dart` ハードコードの廃止、Firestore クエリ＋キャッシュへ移行
3. レビュー機能（構造化フィールド＋自由記述、読取・投稿とも無料、1 人 1 科目 1 件）
4. 「さがす」タブ＋楽単ランキング（学部別 / 系列別）
5. 科目詳細を 2 タブ（レビュー / 過去問・資料）に再編
6. 下タブ再編（さがす / 時間割 / マイページ … 教科書タブは非表示 or "近日公開"）
7. ベルアイコン＋最小限の通知（レビューへの「役に立った」等）

**据え置き（現状のまま）:** 時間割、過去問（現行のポイント制のまま）、参考書リクエスト

**出さない:** 教科書マーケット、チャット作り直し、クレジット作り直し、AppStore 分割、署名 URL

**並行作業（実時間がかかるので今すぐ開始）:**
- 創業者＋友人で、1〜2 年が取る全学共通の主要 100〜150 科目にレビューをシード
- 過去問のストック集め（Phase 2 に向けて）

**ローンチ判定の目安:**
- レビューがある科目のカバー率（主要全学共通科目の X%）
- 登録者数、1 人あたりレビュー閲覧数

### Phase 2 — 2027 年 1 月（試験期）: 過去問層＋クレジット

- Cloud Functions（TypeScript）導入 → Blaze プランへ移行

## 7. 集客プラン

### ローンチ前シード（コールドスタート突破）
- レビュー: 主要 100〜150 科目に最低 1 件
- 過去問（Phase 2 向け）: 自分＋友人・サークル・自治会の過去問集を人気科目に 30〜50 本
- 教科書出品（Phase 3 向け）: 学期末に友人から実出品 20〜30 件

### 効く時期
| 時期 | 需要 | 使い方 |
|---|---|---|
| 履修登録期（10 月頭・4 月頭） | 授業情報がピーク | 本番プッシュ |
| 新歓期（4 月） | 新入生が集結 | 拡散の最大チャンス（Phase 3） |
| 試験期（1 月末・7 月末） | 過去問需要が急増 | Phase 2 のテスト・二次プッシュ |

### 無予算チャネル（京大特化）
- **X**: #春から京大 のリプ欄、京大情報アカウントと相互。「楽単まとめ」を無料公開してアプリへ誘導
- **LINE オープンチャット**: 「京大 履修相談」「新歓」系オプチャで実際に役立つ回答＋リンク（スパムにしない）
- **サークルの新歓 LINE 群**: 友人経由。サークルにも「新歓で使えるツール」として提示
- **立て看・ビラ**: 履修登録期に時計台・生協・各学部に QR。低コスト高効果
- **自治会・生協**: 過去問配布の歴史がある自治会と連携（営利警戒に注意して出方を選ぶ）

### 招待・バイラル
- 招待コード（既存機能）→ 報酬をクレジットに（双方 +3）
- より効くのは機能的バイラル: 時間割を友達とシェア / 教科書出品を X にシェア

### 見る数字
- 履修登録期の「レビューがある科目のカバー率」「登録者数」「1 人あたりレビュー閲覧数」
- North Star: 週次アクティブ（時間割を見に来る）＋ レビュー投稿率

## 8. リスクと対応

| リスク | 対応 |
|---|---|
| 過去問の著作権 → 大学・教員からの削除要請 | A3 の線引き。権利者フォーム＋優先削除キュー。営利で過去問アクセスを販売しない。クレジットは金銭購入不可 |
| Penmark 等の競合 | 土俵をずらす（授業レビュー＋教科書売買。時間割 SNS の正面対決を避ける）。京大単一集中 |
| コールドスタート | レビュー層はコールドスタート依存が低い（創業者が書けば成立）。ローンチ前シード必須 |
| ソロ開発の速度 | 段階ローンチで各フェーズのスコープを絞る。10 月はレビュー層のみ |
| クレジット不正（現状クライアント権威） | Phase 2 で Cloud Functions によるサーバー権威化。Phase 1 の間は内部通貨のみで金銭・広告と未接続なので許容 |
| Flutter Web の SEO・初回ロード | Phase 1 後に技術スタックを再評価。今は動かさない |
| 履修登録期を逃す | Phase 1 のスコープを死守。間に合わない機能は次フェーズへ落とす |

## 9. テスト方針

- **セキュリティルール**: Firebase Emulator Suite でルールのユニットテスト（`@firebase/rules-unit-testing`）。未認証・他大学メール・未検証ユーザー・他人のドキュメント書込を全て拒否できることを検証
- **Course build スクリプト**: 入力（スクレイプ結果）→ 出力（`courses` JSON）の変換をテスト。重複マージ、`courseKey` 正規化のエッジケース（全角スペース、教員名の表記ゆれ）
- **クレジット Function（Phase 2）**: トランザクションの並行性（同時 DL で残高がマイナスにならない）、日次上限、署名 URL の失効
- **Flutter**: レビュー投稿フォームのバリデーション（1 人 1 科目 1 件、必須項目）、集計表示のウィジェットテスト
- **手動 E2E**: 新規登録 → メール検証 → `ku_verified` 付与 → レビュー投稿 → 別アカウントで閲覧・「役に立った」
